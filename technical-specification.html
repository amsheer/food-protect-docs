Technical specification

Food Protect

Mobile (Android, iOS) and web application for food-safety records, multi-vendor, built on the SFBB caterers pack (England and Wales).

Version1.0, for engineering review
Date28 October 2026
BaselineProduct Definition v0.2 (21 Oct 2026) · FSA “Safer Food Better Business for Caterers” · app 4.0.2 · Flutter 3.24.4 (.fvmrc)
ConventionsMUST, SHOULD, MAY as in RFC 2119. Every requirement has an ID. P marks a proposed value to ratify. V marks a value to verify in the backend spike. D marks a decision in the register (section 19).

At a glance

What it isA multi-vendor food-safety records app. Vendors serve clients; clients run sites; staff record checks, temperatures, problems and incidents on phone, tablet or web, with or without a network.
TechnologyFlutter and GetX client. Two data platforms are specified so the choice can be made on facts: Option A, Firebase (Cloud Firestore and Cloud Functions), and Option B, Supabase (PostgreSQL with a TypeScript worker). Full list in 2.3; comparison in 4A.
How to read itPart A tells a builder where to start. Part B holds the foundations, including the Firebase and Supabase options (4A). Part C is the rules. Part D is the screens. Part G lists the decisions still open (section 19). The appendices hold the policies, the API, the wire formats, the texts and the traceability.
Not yet verifiedNeither option has been built or measured; the spike (DPL-04) does that. The Option B schema parses but has not been run. Production Firestore and deployed function settings were not inspected. Food-safety values need an adviser’s sign-off (D-12). Open decisions: D-12, D-19 to D-21, D-25 to D-31.

0. How to build the app from this document

This document is written so that an engineer, or an AI coding assistant working with an engineer, can build Food Protect from it one work package at a time. It is a specification, not a prompt that produces the whole app in one run. Each work package below is a separate task with its own branch, tests and review.

You are a senior engineer building Food Protect: a Flutter 3.24.4 app (FVM, GetX) for Android,

   Do not replace frameworks. Do not upgrade the pinned Flutter version.
3. Treat requirement IDs (ENG-13, SYN-02 ...) as acceptance criteria. Reference them in tests
   and in the pull request description.
4. Never decide items marked D (decision) or V (verify). Stop and ask.

   fvm flutter analyze, fvm flutter test, and the backend test suite of the chosen option.
7. Keep diffs small. No unrelated renames or reformatting. Do not edit generated files.

2. Architecture

2.1 Logical architecture

IDRequirement
ARC-01The system of record is the data platform chosen in D-21: Option A (Cloud Firestore) or Option B (PostgreSQL 15 or later). In both, tenant separation is enforced by the server (rules in A, row-level security in B), never by client code alone. See section 4A.
ARC-02The schema uses standard SQL, RLS and versioned migrations. Provider-only features are avoided so the database can move provider or be dedicated to one vendor.
ARC-03Clients write only through the sync_apply RPC and a small set of admin RPCs (section 7). Direct table INSERT, UPDATE and DELETE are not granted to the authenticated role.

ARC-08The client keeps its layers separate: UI (GetX controllers and views), repositories, local store, sync engine, API client. Business rules that decide pass or fail are shared as one pure Dart package and mirrored by the server on write (ENG-05).

3. Tenancy, identity and authorization

3.1 Hierarchy

IDRequirement
TEN-01Every tenant row reaches its vendor, client and site: directly through vendor_id, client_id and site_id columns, or through its parent row (Appendix E). Runs, problems, incidents and notifications carry all three; answers carry vendor_id and site_id and reach the client through their run; every other site table carries site_id. Where several of these columns exist, composite foreign keys keep them consistent (DAT-03).
TEN-02A user has one login and any number of memberships. A membership is (user, role, scope type, scope id, status, valid_from, valid_to).
TEN-03Effective permissions are the union of the permissions of all active memberships whose scope contains the site.
TEN-04Platform scope does not grant access to client data. Platform staff read client data only through a support access grant: reason, grantee, site, expiry, revocation, all audited (SEC-30).
TEN-05Auditor memberships MUST have valid_to. After expiry all access stops without a data change.
TEN-06A vendor can be moved to a dedicated database with the same schema (ARC-02). Cross-database references are not allowed.

CREATE FUNCTION app.site_ids_with(p_key text) RETURNS SETOF uuid
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT s.id
  FROM sites s
  JOIN clients c ON c.id = s.client_id
  JOIN memberships m ON m.user_id = auth.uid() AND m.status = 'active'
       AND now() >= m.valid_from AND (m.valid_to IS NULL OR now() < m.valid_to)
  JOIN role_permissions rp ON rp.role_id = m.role_id AND rp.permission_key = p_key

     OR (m.scope_type = 'vendor' AND m.scope_id = c.vendor_id)
  UNION
  SELECT g.site_id FROM support_access_grants g
  WHERE g.grantee_id = auth.uid() AND g.revoked_at IS NULL
    AND now() < g.expires_at AND p_key LIKE 'canView%'
$$;

3.4 Shared-device attribution (PIN)

IDRequirement
PIN-01A kitchen device signs in once with a device or manager session bound to a site. Staff attribute each save with a personal PIN.
PIN-02PINs are 4 to 6 digits, stored as argon2id hashes in user_pins with a per-user salt. Plain PINs are never stored or logged.
PIN-035 failed attempts lock that user on that device for 15 minutes P. Lock events are audited. A Location Manager or Client Admin can reset a PIN.
PIN-04verify_pin returns a signing token valid for 120 seconds P. Each record created in that window carries the token’s user as recorded_by.
PIN-05PIN verification works offline against a salted verifier cached on the device (encrypted). The verifier syncs on change. Offline attempts are counted locally and reported on sync.
PIN-06Every record that names a person (recorded_by) also stores attribution. It is server_verified only when the save carries a valid signing token from pin.verify (PIN-04) that the server checked. A save made offline, or without a token, is device_asserted: the person was identified by the PIN check on the device. The app cannot set server_verified; the server decides.
PIN-07On sync the server checks that recorded_by was an active member of the site with canSurvey at recorded_at_device, and that the device belongs to the site. A record that fails is still saved (the work happened), stays device_asserted, appears in an “Unverified attribution” list for the Location Manager and raises a notification. The audit entry holds the device id and the session that signed the device in.
PIN-08Reports, PDFs and inspector views mark device_asserted records with a symbol and the text “Recorded on the device; person confirmed by PIN on the device”. The day sign-off screen shows how many records of the day are marked this way.
PIN-09Attribution is no stronger than the device. The Location Manager’s signature of the day (days.sign) is the control that confirms the day’s records, and the spec does not claim that a device-asserted record proves who made it.

4. Data model

4.1 Conventions

IDRule
DAT-01Primary keys are uuid. Records created on devices use UUIDv7 generated on the device, so retries are idempotent and keys sort by time.
DAT-02All timestamps are timestamptz in UTC. Local dates (due_local_date) are stored as date together with the site time zone.
DAT-03Tenant tables use composite foreign keys so the denormalised ids cannot disagree: FOREIGN KEY (site_id, vendor_id) REFERENCES sites (id, vendor_id), with UNIQUE (id, vendor_id) on the parent.
DAT-04Foreign keys are ON DELETE RESTRICT. Records are never hard-deleted by the application. Deactivation uses a status column.
DAT-05Records are append-only. A correction is a new row that points to the old one (supersedes_id). A signed day is locked.
DAT-06Every record row stores recorded_by, recorded_at_device and received_at (server time).
DAT-07Published checklist versions are immutable. A trigger rejects UPDATE and DELETE of a published version and its questions, except status change to retired.
DAT-08Enumerations are text with CHECK constraints, not Postgres enums, except scope_type. This keeps migrations simple.
DAT-09Every foreign key and every RLS predicate column is indexed. Tenant tables have an index leading with site_id or vendor_id.
DAT-10Names are snake_case. Table names are plural. SQL keywords are uppercase.
DAT-11Personal data lives in a small set of columns (name, email, phone, PIN hash, device id). They are listed in the retention table (SEC-40).
DAT-12answers is partitioned by month on received_at before it passes 100 million rows P. The primary key then becomes (id, received_at) and idempotency moves to sync_ops.

Firebase and Supabase both hold the data. Everything the user sees and every business rule in this document is the same with either one. This follows app.site_ids_with in Option B, and a role change applies on the next request with no sign-out (TEN-12), because nothing is stored in the sign-in token.

access/{uid} = {
  "sites":   { "canViewChecklist": ["<site id>", …], "canViewReport": […], … },
  "clients": { "canViewChecklist": ["<client id>", …], … },   // covers every site of the client, including new ones
  "vendors": { "canViewChecklist": ["<vendor id>", …], … },
  "expiresAt": null              // set only when every grant expires (Auditor), TEN-05
}
rules_version = '2';
service cloud.firestore {
  match /databases/{db}/documents {
    function acc() { return get(/databases/$(db)/documents/access/$(request.auth.uid)).data; }
    function live() { return acc().expiresAt == null || request.time < acc().expiresAt; }
    // Does the caller hold permission k for the site, client or vendor named in document d?
    function can(k, d) {
      return request.auth != null && live() && (
        d.siteId   in acc().sites.get(k, []) ||
        d.clientId in acc().clients.get(k, []) ||
        d.vendorId in acc().vendors.get(k, []));
    }
    // The ids written by the app must match the site (stops a document being filed under another vendor).
    function consistent(d) {
      let s = get(/databases/$(db)/documents/sites/$(d.siteId)).data;
      return s.vendorId == d.vendorId && s.clientId == d.clientId;
    }

    match /runs/{id} {
      allow read: if can('canViewChecklist', resource.data) || can('canViewReport', resource.data);
      allow create: if false;                                  // the scheduler function creates runs
      allow update: if can('canSurvey', resource.data)
        && resource.data.status == 'open' && request.resource.data.status == 'submitted'
        && request.resource.data.diff(resource.data).affectedKeys()
             .hasOnly(['status','answers','submittedAt','submittedBy','recordedAtDevice','pinUserId','version']);
      allow delete: if false;
    }
    match /diaryNotes/{id} {                                    // append-only
      allow read: if can('canViewChecklist', resource.data);
      allow create: if can('canSurvey', request.resource.data) && consistent(request.resource.data);
      allow update, delete: if false;
    }
    match /auditLog/{id} { allow read: if can('canManageReporting', resource.data); allow write: if false; }
    match /appConfig/{key} { allow read: if true; allow write: if false; }
    match /{document=**} { allow read, write: if false; }      // everything else is denied
  }
}

SYN-43Sign-out is blocked while the outbox has ops that are not sent, with an explanation and an export option.
SYN-50Record states shown in the UI: waiting (in outbox), sending (request in flight), sent (accepted), failed (rejected or quarantined). Count of non-sent items is visible in the header.

CREATE SCHEMA IF NOT EXISTS app;

-- Sites where the caller holds permission p_key: app.site_ids_with (section 3.3).
-- The functions below follow the same pattern: SECURITY DEFINER, fixed search_path, a SETOF uuid.
CREATE FUNCTION app.client_ids_with(p_key text) RETURNS SETOF uuid
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT c.id FROM clients c
  JOIN memberships m ON m.user_id = auth.uid() AND m.status = 'active'
       AND now() >= m.valid_from AND (m.valid_to IS NULL OR now() < m.valid_to)
  JOIN role_permissions rp ON rp.role_id = m.role_id AND rp.permission_key = p_key
  WHERE (m.scope_type = 'client' AND m.scope_id = c.id)
     OR (m.scope_type = 'vendor' AND m.scope_id = c.vendor_id)
$$;
CREATE FUNCTION app.vendor_ids_with(p_key text) RETURNS SETOF uuid
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT m.scope_id FROM memberships m
  JOIN role_permissions rp ON rp.role_id = m.role_id AND rp.permission_key = p_key
  WHERE m.user_id = auth.uid() AND m.status = 'active' AND m.scope_type = 'vendor'
    AND now() >= m.valid_from AND (m.valid_to IS NULL OR now() < m.valid_to)
$$;
CREATE FUNCTION app.platform_has(p_key text) RETURNS boolean
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT EXISTS (
    SELECT 1 FROM memberships m
    JOIN role_permissions rp ON rp.role_id = m.role_id AND rp.permission_key = p_key
    WHERE m.user_id = auth.uid() AND m.status = 'active' AND m.scope_type = 'platform'
      AND now() >= m.valid_from AND (m.valid_to IS NULL OR now() < m.valid_to))
$$;
-- Any membership at all: used to read the structure rows a user belongs to.
CREATE FUNCTION app.my_vendor_ids() RETURNS SETOF uuid
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT DISTINCT c.vendor_id FROM clients c JOIN memberships m ON m.user_id = auth.uid() AND m.status = 'active'
    AND now() >= m.valid_from AND (m.valid_to IS NULL OR now() < m.valid_to)
  WHERE (m.scope_type = 'vendor' AND m.scope_id = c.vendor_id)
     OR (m.scope_type = 'client' AND m.scope_id = c.id)
     OR (m.scope_type = 'site' AND m.scope_id IN (SELECT id FROM sites WHERE client_id = c.id))
$$;
CREATE FUNCTION app.my_client_ids() RETURNS SETOF uuid
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT DISTINCT c.id FROM clients c JOIN memberships m ON m.user_id = auth.uid() AND m.status = 'active'
    AND now() >= m.valid_from AND (m.valid_to IS NULL OR now() < m.valid_to)
  WHERE (m.scope_type = 'vendor' AND m.scope_id = c.vendor_id)
     OR (m.scope_type = 'client' AND m.scope_id = c.id)
     OR (m.scope_type = 'site' AND m.scope_id IN (SELECT id FROM sites WHERE client_id = c.id))
$$;
CREATE FUNCTION app.my_site_ids() RETURNS SETOF uuid
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT s.id FROM sites s JOIN clients c ON c.id = s.client_id
  JOIN memberships m ON m.user_id = auth.uid() AND m.status = 'active'
    AND now() >= m.valid_from AND (m.valid_to IS NULL OR now() < m.valid_to)
  WHERE (m.scope_type = 'site' AND m.scope_id = s.id)
     OR (m.scope_type = 'client' AND m.scope_id = c.id)
     OR (m.scope_type = 'vendor' AND m.scope_id = c.vendor_id)
$$;
-- Users the caller may see and administer: members of scopes where the caller holds canManageUsers.
CREATE FUNCTION app.managed_user_ids() RETURNS SETOF uuid
LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT m.user_id FROM memberships m
  WHERE (m.scope_type = 'site' AND m.scope_id IN (SELECT app.site_ids_with('canManageUsers')))
     OR (m.scope_type = 'client' AND m.scope_id IN (SELECT app.client_ids_with('canManageUsers')))
     OR (m.scope_type = 'vendor' AND m.scope_id IN (SELECT app.vendor_ids_with('canManageUsers')))
$$;
